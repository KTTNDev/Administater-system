# ลำดับดำเนินงานจัดซื้อจัดจ้าง รุ่น 1.7.0

หน้าเดิมแบ่งส่วนกรอกตามส่วนหัว เนื้อหา ผู้ลงนาม และหลักฐาน รุ่นนี้เพิ่มลำดับงานจริงด้านบน ส่วนกรอกเหล่านั้นเป็นเครื่องมือแก้ไขข้อมูลของขั้นที่เลือก โดยยังกรอกบิลร่วมเพียงครั้งเดียว

## ลำดับหลัก

1. ขออนุมัติจัดซื้อ/จัดจ้าง — D01
2. ขออนุมัติมอบหมายร่างขอบเขตงาน — D02
3. ร่างขอบเขตงาน/คุณลักษณะเฉพาะ — D04
4. รายงานผลการร่างขอบเขตงาน — D03
5. รายงานขอซื้อ/ขอจ้าง — D05
6. คำสั่งแต่งตั้งผู้ตรวจรับ — D06
7. รายงานผลและขออนุมัติสั่งซื้อ/จ้าง — D07
8. ประกาศผู้ชนะ — D08
9. ใบสั่งซื้อ/จ้างและกำหนดสัญญา — D09
10. ข้อมูลสาระสำคัญจาก e-GP — D10
11. ข้อมูลสัญญา e-GP ที่แสดงใน e-LAAS — E01
12. ใบตรวจรับและผลตรวจรับตามจริง — D11
13. รายงานผลตรวจรับ — D12
14. รายงานวิธีการและหลักฐาน — D13
15. ขออนุมัติเบิกจ่าย — D14
16. ส่งตั้งหนี้ คลังลงรับ และคลังส่งเอกสารกลับให้ทำฎีกา
17. อัปโหลด PDF ฎีกาจาก e-LAAS และสแกนฉบับลงนาม — V01
18. ส่งฎีกาและคลังลงรับรอบสองเพื่อจบงาน

รหัส D03/D04 ของไฟล์เดิมคงไว้ เปลี่ยนลำดับแสดง/พิมพ์ให้ TOR มาก่อนรายงานผลร่าง ไม่เปลี่ยนหมายเลขอ้างอิงหรือไฟล์ประวัติย้อนหลัง

## การใช้งานแต่ละขั้น

เลือกงานแล้วระบบเปิดขั้นแรกที่ยังไม่ครบ ปุ่ม “เอกสารและลายเซ็นของขั้นนี้” รวมการสร้างฉบับเดียว แนบไฟล์ต้นทาง เลือกฉบับใช้งาน แนบสแกน ตรวจลายเซ็น และยืนยันตรวจทาน

การสร้างในขั้นนี้เลือกไฟล์เป็นฉบับใช้งานให้ แต่ไม่อนุมัติ ไม่สร้างลายเซ็น และไม่ทำให้ขั้นเสร็จเอง การแนบสแกนยังต้องให้เจ้าหน้าที่ตรวจและยืนยัน ปุ่มผ่านขั้นตรวจทั้งขั้นปัจจุบันและขั้นก่อนหน้าบนเซิร์ฟเวอร์

สามารถเปิดดูหรือเตรียมร่างล่วงหน้าได้ เครื่องมือสร้างทั้งชุดยังอยู่ในส่วนพับ “เครื่องมือทั้งชุด — เตรียมร่างล่วงหน้า” แต่การสร้างไฟล์ไม่ทำให้ผ่านขั้น ช่องที่ไม่ต้องใช้ต้องระบุเหตุผลยกเว้นชัดเจน V01 ยกเว้นไม่ได้

วันครบสัญญากรอกในขั้น D09 ผลตรวจรับกรอกในขั้น D11 เมื่อแก้ข้อมูลบิล/ข้อความ เอกสารที่อ้างข้อมูลที่เปลี่ยนจะต้องตรวจหรือสร้างใหม่ ไฟล์เดิมไม่ถูกทับ ระหว่างกำลังสร้างหรือบันทึกระบบล็อกส่วนกรอกเพื่อไม่ให้ข้อความที่พิมพ์ซ้อนสูญหาย

## ฎีกาและหลักฐานคลัง

ขั้น V01 เปิดแนบเมื่อสถานะเป็นรับเอกสารกลับเพื่อทำฎีกาแล้ว ช่อง PDF ต้นทางจาก e-LAAS แยกจากช่องสแกนลงนาม ผู้ใช้ตรวจลายเซ็นและยืนยันเนื้อหาก่อนส่งรอบสอง ตัวอย่าง PDF แสดงในฝั่งขวา

วันส่ง วันลงรับ เลขรับ ผู้บันทึก และหลักฐานยังบันทึกแยกตามเหตุการณ์จริง งานจบเมื่อคลังลงรับรอบสอง ไม่ใช่สถานะจ่ายเงินจริง และระบบไม่สร้างเหตุการณ์รับส่งแทนผู้ใช้

## งานเดิมและตัวอย่างทดสอบ

ใช้ตารางเดิมและคำนวณขั้นจากเอกสาร/การตรวจที่บันทึกไว้ ไม่มีการย้ายฐานข้อมูล ชุดส่งคลังเดิมที่ตรึงไว้ใช้ไฟล์เดิมเป็นหลักฐานและไม่ถูกสั่งสร้างใหม่เพียงเพราะเพิ่มหน้าลำดับงาน

ตัวอย่างสั้นและยาวมี `sample: true` แสดงในส่วน “ตัวอย่างสำหรับทดสอบ” แยกจากงานจริง ไม่ถูกนำไปเติมรายชื่อเริ่มต้นหรือแสดงในปฏิทินสัญญางานจริง งานเก่าที่ไม่มีฟิลด์นี้อ่านเป็นงานจริงโดยไม่แก้ JSON ที่จัดเก็บ ไม่เปลี่ยนสถานะงานจริง/ตัวอย่างของงานเดิมผ่านการแก้ฟอร์ม

การเพิ่มตัวอย่างในฐานจริงทำได้ด้วย `scripts/seed-procurement-journey-samples.mjs --real` เฉพาะเมื่อได้รับอนุญาตจากผู้ใช้ ตัวสคริปต์ตรวจ instance ระบบจริง เพิ่มเฉพาะตัวอย่างที่ระบุ และไม่สร้างซ้ำหรือทับความคืบหน้าที่ผู้ใช้เริ่มแก้ไขแล้ว ตัวอย่างเริ่มสถานะเตรียมเอกสาร ไม่มีสแกนอนุมัติหรือเหตุการณ์คลังที่จำลองล่วงหน้า

ตัวอย่างสั้นเป็นงานซื้อวัสดุสำนักงาน 2 รายการ ยอด 1,366 บาท ตัวอย่างยาวเป็นงานจ้างซ่อมบำรุง 2 รายการ ยอด 3,400 บาท พร้อมข้อความจำลองยาวในร่างทั้ง 14 ฉบับ จำนวนหน้าอ้างอิง PDF ที่พิมพ์จริง กรณี Word นับหน้าว่างแฝงในเอกสาร PDF หน้าเดียว ใช้ข้อความเนื้อหาหลักทั้งหน้าสำหรับตรวจจัดหน้า ส่วนเอกสารหลายหน้ายังคงหยุดเมื่อข้อมูลหน้าไม่ตรงกัน

ลำดับนี้เป็นกระบวนงานตามที่ผู้ใช้กำหนด ไม่ได้ขยายการรับรองว่าแม่แบบครอบคลุมทุกวิธีจัดซื้อหรือเชื่อม API e-GP/e-LAAS
