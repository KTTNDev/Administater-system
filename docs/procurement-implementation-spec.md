# ข้อกำหนดพัฒนางานจัดซื้อจัดจ้างและเอกสารทั้งกระบวนงาน

วันที่ 15 พฤศจิกายน 2569

คำยืนยันล่าสุด: ผู้ใช้ยอมรับรูปแบบ D07 ที่อิงต้นฉบับแล้ว และให้ตัวอักษรเตือนสีแดงเปลี่ยนเป็นสีดำในฉบับใช้งาน ระบบหลักต้องเริ่มจากงานจัดซื้อ/จัดจ้างหนึ่งเรื่อง กรอกข้อมูลเฉพาะบิล/ใบเสนอราคาครั้งนั้นครั้งเดียว แล้วสร้างเอกสารครบชุดที่ใช้กับแนวทางนั้น โดยทุกฉบับยังแก้ได้ อ่าน [กระบวนงานและผลค้นหลักเกณฑ์ล่าสุด](procurement-procedures-20261115.md) ประกอบ การเลือกแนวทางและข้อยกเว้น e-GP เป็นคนละข้อมูล ไม่ใช้ยอดเงินอย่างเดียวหรือใช้ชื่อ ว322 แทนวิธีตามกฎหมาย

สถานะ: เริ่มพัฒนาช่วง A1 แล้ว มีห้องทดลอง D07 สองโหมด พร้อมตัวอย่าง A4, PDF, Word และการนำ Word กลับมาตรวจความต่าง ดู [ผลพัฒนาและข้อจำกัดปัจจุบัน](procurement-stage-a-progress.md) ยังไม่ถือว่า Stage A หรือระบบทั้งกระบวนงานเสร็จ

ผลแก้ไขเรื่องต้นฉบับ: มีหน้า D07 ใหม่ที่ใช้สำเนา Word จริงแล้ว กรณีข้อมูลเดิมได้ Word ตรงต้นฉบับทุกไบต์และภาพต่าง 0 พิกเซลที่ 120 dpi บนเครื่องนี้ ตัวอย่างแก้ 7 ช่องยังเป็นหน้าเดียวและรักษาโครงเดิม ดู [ผลตรวจแม่แบบต้นฉบับ](procurement-template-fidelity.md) การเพิ่มย่อหน้า/รายการ การแก้ใบต่อ และการเชื่อม Word ไป–กลับกับแม่แบบใหม่นี้ยังต้องทำต่อ

ข้อแก้ไขลำดับงานจากผู้ใช้: ห้องทดลอง A1 สร้างเค้าโครงเอกสารขึ้นใหม่และยังไม่เหมือนต้นฉบับ ตำแหน่งลงนาม ตราครุฑ และรูปแบบข้อความจึงยังไม่ผ่านความต้องการ ให้ทำความเหมือนต้นฉบับก่อนขยายฟังก์ชันอื่น ผลทดสอบข้อมูล/Word ไป–กลับเดิมไม่ใช่หลักฐานว่าแม่แบบเหมือนต้นฉบับ

### เกณฑ์ที่ต้องผ่านก่อนขยายฟังก์ชัน

1. ยึดไฟล์ต้นฉบับที่ผู้ใช้ส่งเป็นแม่แบบหลัก เริ่มจาก D07 `7.รายงานพิจารณาผล.docx` และเก็บต้นฉบับพร้อม SHA-256 โดยไม่แก้ทับ
2. เปิดตรวจหน้าพิมพ์ต้นฉบับทุกหน้าด้วย Microsoft Word เป้าหมาย เก็บภาพ/PDF อ้างอิงและหลักฐานรูปแบบจริง การอ่านเฉพาะข้อความหรือ XML ยังไม่ถือว่าตรวจความเหมือนครบ
3. ใช้สำเนาไฟล์ต้นฉบับเป็นฐาน รักษาตราครุฑและความสัมพันธ์รูป กล่องข้อความ/ตำแหน่งยึด รูปแบบตัวอักษร ย่อหน้า แท็บ ระยะขอบ ตาราง ช่องลงนาม และหัวท้ายกระดาษ ห้ามสร้างเอกสารว่างหรือใช้ grid/แม่แบบทั่วไปทดแทนโครงเดิมเพื่อความสะดวก
4. ทดสอบกรณีข้อมูลเดิมไม่เปลี่ยนก่อน ผลลัพธ์ต้องคงรูปแบบและจำนวนหน้าเดิม เทียบภาพทุกหน้ากับต้นฉบับและตรวจชิ้นส่วนไฟล์ที่ต้องคงไว้ ไม่มีการรับรองว่าเหมือน 100% โดยอาศัยเพียงความรู้สึกหรือผลทดสอบข้อมูล
5. เมื่อกรณีข้อมูลเดิมผ่านแล้ว จึงผูกช่องข้อมูลกลางและแก้เฉพาะจุดที่กำหนด ทดลองชื่อ วันที่ ราคา และเนื้อหาทีละชนิด พร้อมเทียบว่าการเปลี่ยนแปลงจำกัดอยู่ในจุดที่ตั้งใจ กรณีเนื้อหายาวขึ้นอาจมีการตัดหน้าใหม่ตามเนื้อหา โดยคงรูปแบบต้นฉบับ
6. เก็บข้อความตกค้างของต้นฉบับไว้ในหลักฐานอ้างอิงก่อน แยกการแก้เนื้อหา เช่น ใบต่อผิดเรื่อง/วันที่ ออกจากการพิสูจน์ความเหมือน การแก้ที่ผู้ใช้สั่งไว้ต้องมีรายการความต่างชัดเจน
7. การเลือกแนวคิด “เรียงเยื้องตามสายเสนอ” ไม่ใช่การอนุญาตให้แทนตำแหน่งจริงในต้นฉบับด้วยเค้าโครงที่สร้างใหม่ รูปแบบทางเลือกและการจัดวางอิสระทำภายหลังจากฐานต้นฉบับผ่านแล้ว

การพัฒนาลำดับถัดไปให้เริ่มจากเกณฑ์ข้างต้นก่อนแม่แบบอื่น ทะเบียนสัญญา และกระบวนงานกองคลัง ส่วนข้อมูลกลาง การเก็บรุ่น และการตรวจความต่างที่ทำแล้วเก็บไว้ใช้ต่อได้ แต่ไม่ถือว่าเป็นการผ่านเกณฑ์ด้านรูปแบบ

อัปเดตขอบเขตล่าสุด: D05–D11 เลือกเป็นรายฉบับได้ว่าจะใช้ไฟล์จาก e-GP โดยตรง หรือร่างในระบบเราจากข้อมูล e-GP ที่ผู้ใช้นำมากรอก โดยเก็บต้นฉบับอ้างอิงไว้ ดูหัวข้อ 6.1 ส่วน D10 คือข้อมูลสาระสำคัญ e-GP ข้อมูลสัญญามีต้นทาง e-GP แต่แสดงและแคปจาก e-LAAS และงานจบเมื่อกองคลังลงรับชุดฎีการอบที่สอง ดูหัวข้อ 20–22 ประกอบ ไม่ถือว่าฉบับที่ร่างในระบบเราเป็นไฟล์ที่ e-GP ออกให้ และไม่รอจ่ายเงินจริงจึงปิดงาน

## 1 ผลลัพธ์ที่ผู้ใช้ต้องการ

สร้างเรื่องจัดซื้อจัดจ้างหนึ่งเรื่อง กรอกข้อมูลที่เปลี่ยนจากงานเก่าเพียงครั้งเดียว แล้วสร้างเอกสารตามขั้นตอนจากข้อมูลกลางเดียวกัน ผู้ใช้แก้เอกสารในระบบหรือ Word ภายนอกได้ เมื่อนำ Word กลับ ระบบต้องแสดงความต่างและให้เลือกนำกลับเป็นรายจุด การจัดหน้า ช่องลงนาม และข้อความใบต่อสัมพันธ์กับเนื้อหาของหนังสือฉบับนั้น

ปัญหาปัจจุบันคือคัดลอก Word จากงานเก่าแล้วแก้ชื่อร้าน รายการ ราคา บุคคล วันที่ และเลขอ้างอิงทีละไฟล์ ทำให้เสียเวลา มีข้อความตกค้าง และต้องจัดหน้า/ขยับช่องเซ็นใหม่ การพัฒนาต้องแก้ปัญหานี้ก่อนเพิ่มแดชบอร์ดหรือระบบกฎที่ซับซ้อน

## 2 ข้อสรุปที่ผู้ใช้ยืนยัน

| เรื่อง | ข้อกำหนด |
| --- | --- |
| สายลงนามหลัก | ผู้เสนอ → ผู้อำนวยการกอง → ปลัด/ผู้ปฏิบัติราชการแทน → นายก/ผู้ปฏิบัติราชการแทน รวม 4 จุด |
| การแก้เอกสาร | รองรับทั้งการแก้ในระบบและ Word ภายนอก พร้อมตรวจความต่างเมื่อนำกลับ |
| ข้อความหน้าต่อ | ใช้ “ใบต่อบันทึกข้อความ เรื่อง … ที่ … ลงวันที่ …” โดยอ้างจากข้อมูลหน้าแรกของหนังสือฉบับเดียวกัน |
| บริหารสัญญา | กำหนดเวลาและรายการที่ต้องทำตามสัญญา พร้อมแนะนำลำดับงานตามกำหนดและงานที่ต้องเสร็จก่อน |
| แหล่งเอกสาร | D05–D11 เลือกได้รายฉบับระหว่างใช้ไฟล์ e-GP กับร่างในระบบจากข้อมูล e-GP; ขั้นที่เหลือซึ่งทำเองใช้ตัวร่างเดิม |
| ข้อมูลสัญญาที่แคป | ข้อมูลต้นทาง e-GP แต่แสดงในหน้าจอ e-LAAS ต้องบันทึกที่มาทั้งสองส่วน |
| คลังรอบแรก | ส่งตั้งหนี้และเก็บหลักฐานลงรับ รอเจ้าหน้าที่คลังแจ้งและส่งเอกสารกลับให้เจ้าของเรื่องทำฎีกาต่อ |
| คลังรอบสอง | พิมพ์ชุดฎีกาจาก e-LAAS ให้ผู้มีอำนาจลงนาม ส่งคลังอีกครั้ง และปิดงานเมื่อมีหลักฐานลงรับรอบนี้ |

แบบเรียงเยื้องตามสายเสนอใช้เป็นต้นแบบหลักตามแนวทางที่เสนอ พร้อมตัวเลือกสองคอลัมน์และจัดวางเอง พิกัดจริง ระยะว่าง และแบบพิมพ์จะปรับจากตัวอย่างที่ตรวจรับอีกครั้ง ไม่ถือว่าภาพร่างเป็นหลักฐานว่าเค้าโครงผ่านตรวจตามระเบียบแล้ว

การยืนยันสายลงนามหลักไม่บังคับให้เอกสารทั้ง 14 ฉบับมีผู้ลงนามเหมือนกันทุกคน แต่ละแม่แบบเลือกบทบาทที่ต้องใช้ได้ เช่น ผู้ตรวจรับ ผู้รับรองภาพ หรือผู้รับใบสั่ง

## 3 ขอบเขตพัฒนาชุดแรกและส่วนขยาย

ชุดแรกทำงานซื้อวัสดุสำนักงานให้ครบตั้งแต่เตรียมเรื่อง บริหารกำหนดตามสัญญา รวบรวมเอกสารจากผู้ค้า/e-GP/e-LAAS พิมพ์ A4 เสนอเซ็น ส่งตั้งหนี้รอบแรก รอคลังส่งกลับเพื่อทำฎีกา และส่งชุดฎีกาที่ลงนามแล้วรอบสอง งานของเจ้าของเรื่องจบเมื่อคลังลงรับรอบสอง การจ่ายเงินจริงเป็นข้อมูลติดตามเพิ่มเติม ไม่ใช่เงื่อนไขปิดงานนี้

รองรับรายการกระบวนงาน D01–D14 และหลักฐานเพิ่มตามหัวข้อ 6 เอกสารทำเองและ D05–D11 ที่เลือกโหมดร่างในระบบต้องสร้าง/แก้และใช้ Word ไป–กลับได้ ส่วนโหมดใช้ไฟล์ภายนอกเก็บต้นฉบับกับข้อมูลอ้างอิงโดยไม่สร้างทับ ความหมายของ “ครบชุด” คือครบเอกสารและหลักฐานตามโหมดที่เลือก ไม่อ้างว่าฉบับร่างของระบบเราเป็นไฟล์ที่ e-GP/e-LAAS ออกให้

งานจ้างซ่อม งานบริการ งานก่อสร้าง วิธีอื่น และกรณีเร่งด่วนเป็นส่วนขยายตามตัวอย่างและกฎที่ตรวจเพิ่ม ออกแบบประเภทงานและแม่แบบให้เพิ่มได้ แต่ไม่ประกาศว่ารองรับกรณีเหล่านั้นครบโดยอาศัยชุดซื้อวัสดุเพียงชุดเดียว

OCR หรือ AI อ่านใบเสนอราคาเป็นส่วนเพิ่มภายหลัง รุ่นแรกกรอกและตรวจข้อมูลจากเอกสารได้ครบโดยไม่ต้องพึ่งบริการภายนอก ไม่ส่งไฟล์ของผู้ใช้ไปบริการภายนอกอัตโนมัติ

## 4 แหล่งข้อมูลหลักและความสัมพันธ์

แยกข้อมูลเป็น 4 ชั้น:

1. **ข้อมูลกลางของเรื่อง**: องค์กร เหตุผล ปีงบประมาณ แหล่งเงิน รายการพัสดุ ข้อเสนอ ผู้ขายที่เลือก ผู้เกี่ยวข้อง และเหตุการณ์
2. **ข้อมูลเฉพาะเอกสาร**: ชนิดเอกสาร เรื่อง เลขที่ วันที่ ผู้รับ บทบาทผู้ลงนาม เนื้อหาเฉพาะ และรูปแบบช่องลงนาม
3. **ฉบับเอกสารที่สร้าง**: สำเนาข้อมูลกลางที่ใช้ รุ่นแม่แบบ รุ่นเนื้อหา ค่าที่แก้เฉพาะฉบับ และประวัติการส่งออก
4. **หลักฐานจริง**: ใบเสนอราคา บิล ส่งมอบ ตรวจรับ ฉบับลงนาม ภาพ และการรับ/ตีกลับจากคลัง

ข้อมูลที่เปลี่ยนกลางเรื่องต้องแสดงรายการฉบับร่างที่ได้รับผลกระทบ การแก้เฉพาะฉบับต้องมีเครื่องหมายแสดงว่าแตกต่างจากข้อมูลกลางและเลือกคืนค่ากลางได้

เลขหนังสือ วันที่ และเรื่องของแต่ละฉบับไม่ใช้ตัวแปรเดียวกันทั้งแฟ้ม ส่วนข้อความใบต่อของฉบับใดต้องอ่านจากข้อมูลเฉพาะฉบับนั้น ไม่มีช่องให้พิมพ์เรื่อง/เลข/วันที่ท้ายหน้าซ้ำแยกอิสระ

การแก้ทะเบียนร้านค้าหรือบุคลากรไม่เปลี่ยนข้อมูลในฉบับที่ออกแล้ว เก็บสำเนาชื่อ ที่อยู่ ตำแหน่ง และข้อความปฏิบัติราชการแทน ณ รุ่นที่ใช้จริง

| รายการ | รหัสรายการคงที่ ชื่อ คุณลักษณะ จำนวน หน่วย ราคา ส่วนลด ภาษี และประเภทวัสดุ/ครุภัณฑ์ |
| ข้อเสนอ | ผู้เสนอ เลข/วันที่ใบเสนอราคา ราคาต่อรายการ เงื่อนไข หลักฐาน และผลคัดเลือก |
| ผู้ขาย | ชื่อ ประเภท เลขผู้เสียภาษี สาขา ที่อยู่ ผู้ติดต่อ สถานะภาษี และข้อมูลรับเงินตามความจำเป็น |
| บุคลากร | ชื่อ ตำแหน่ง บทบาท ข้อความรักษาราชการ/ปฏิบัติราชการแทน เอกสารอ้างอิงอำนาจ และช่วงเวลามีผล |
| จำนวนเงิน | ราคากลาง วงเงินอนุมัติ ราคาที่ตกลง ยอดส่งมอบ ยอดบิล ยอดเสนอเบิก ฐาน/อัตราภาษี รายการหัก และสุทธิ แยกตามความหมาย |
| วันที่/เลข | เหตุการณ์แต่ละขั้น เลขหนังสือ คำสั่ง ใบสั่ง บิล ตรวจรับ e-GP และ e-LAAS แยกจากกัน |
| ไฟล์ | เจ้าของเรื่อง/เอกสาร/รายการ/งวด ชนิดไฟล์ ขนาด hash ต้นฉบับ ผู้บันทึก เวลา และสถานะตรวจ |
| สัญญา | เลข/ประเภทข้อตกลง คู่สัญญา วันลงนาม วันเริ่ม/สิ้นสุด งวด/กำหนดส่ง งานที่ต้องทำก่อน ระยะเผื่อ วันเป้าหมายภายใน และหลักฐานแก้ไขสัญญา |
| ที่มาหลักฐาน | ผู้ส่ง/ผู้ออก ระบบต้นทาง ระบบที่แสดงข้อมูล ช่องทางได้ไฟล์ วันที่รับ/แคป รุ่น และรายการ/สัญญาที่เกี่ยวข้อง |
| โหมดเอกสาร | documentMode, dataOrigin, renderedBy, sourceFileId/sourceReference, workingRevisionId และ selectedUseRevisionId แยกข้อมูลอ้างอิงจากฉบับที่เลือกใช้งาน |
| ส่งกองคลัง | รอบตั้งหนี้หรือรอบฎีกา เลขชุดส่ง รุ่นเอกสารในชุด วันที่ส่ง/ลงรับ ผู้รับ เลขรับ ภาพตราลงรับ และการส่งเอกสารกลับ |

จำนวนรายการคำนวณจากแถวรายการ ไม่ปนกับจำนวนหน่วย เช่น 2 รายการอาจเป็นกล่อง 2 ใบและตลับเมตร 1 ตลับ ไม่ย้อนหาราคาต่อชิ้นจากยอดเหมารวมโดยไม่มีหลักฐาน

ใช้จำนวนสตางค์หรือเลขฐานสิบที่มีนโยบายปัดเศษชัดเจน ไม่ใช้ผล floating point ดิบเป็นยอดเงิน ไม่กำหนด VAT/หัก ณ ที่จ่ายจากคำว่า “ซื้อ” หรือ “จ้าง” เพียงอย่างเดียว

เก็บวันที่เป็น ISO ค.ศ. แสดง พ.ศ. ตามรูปแบบเอกสาร และแยกปีงบประมาณจากปีวันที่หนังสือ

### 6.1 ทางเลือก D05–D11 เป็นรายฉบับ

ให้เลือกแยกกันในแต่ละเรื่องและแต่ละชนิดเอกสาร เช่น D05 ใช้ไฟล์ e-GP แต่ D07 ร่างเอง ไม่เป็นสวิตช์เดียวที่บังคับทั้งชุด

| โหมด | หน้าทำงาน | ฉบับที่ใช้พิมพ์/ส่งคลัง |
| --- | --- | --- |
| ใช้ไฟล์จาก e-GP | แนบ/ดูต้นฉบับ ระบุเลข วันที่ และข้อมูลอ้างอิง จัดลำดับและแนบสแกนลงนาม | รุ่นไฟล์ e-GP ที่ผู้ใช้เลือก |
| ร่างในระบบจากข้อมูล e-GP | กรอก/คัดลอกข้อมูลจากระบบภายนอก เติมจากข้อมูลกลาง ตรวจแหล่งที่มารายช่อง แล้วใช้ฟอร์ม A4/ช่องลงนาม/ใบต่อและ Word ไป–กลับ | รุ่นเอกสารที่ระบบเราสร้างและผู้ใช้เลือก |

ทั้งสองโหมดมีได้พร้อมกันเป็นต้นฉบับอ้างอิงกับฉบับทำงาน แต่ต้องมี “ฉบับที่เลือกใช้งาน” ชัดเจน ก่อนออกชุดส่งให้เลือกหนึ่งฉบับหลักต่อรายการ เอกสารต้นทางแนบเป็นหลักฐานประกอบเพิ่มได้โดยตั้งใจ ไม่พิมพ์ซ้ำทั้งสองฉบับเป็นรายการหลักอัตโนมัติ

เก็บข้อมูลต้นทางกับผู้สร้างฉบับแยกกัน เช่น dataOrigin=e-GP และ renderedBy=Sarabun สำหรับฉบับร่าง ระบบไม่อ้างว่าได้ดึง e-GP ผ่าน API เพียงเพราะผู้ใช้คัดลอกข้อมูลมากรอก ไม่เดาเลขโครงการ เลขสัญญา วันที่ ผลคัดเลือก หรือผลตรวจรับที่ยังไม่ได้ระบุ

ถ้ามีไฟล์/ภาพอ้างอิงให้เชื่อมกับร่างและเก็บต้นฉบับ ถ้ามีเพียงข้อมูลที่คัดลอกมาให้ระบุที่มา/เลขอ้างอิงตามที่มีจริงและแสดงว่ายังไม่มีไฟล์ต้นทาง ไม่สร้างไฟล์อ้างอิงหรืออ้างว่าแนบแล้วเอง

การสลับโหมดไม่ลบร่างหรือไฟล์เดิม ให้กลับมาเลือกต่อได้ และไม่เปลี่ยนข้อมูลกลางทั้งเรื่องโดยอัตโนมัติ หากข้อมูลกรอกไม่ตรงกับต้นฉบับที่มี ให้แสดงความต่างที่ตรวจได้พร้อมระบุวิธีตรวจ ไม่อ้างว่าตรวจข้อความจากภาพ/PDF ได้ครบหากยังไม่มีตัวอ่านที่รองรับ

เลขเอกสารที่ระบบร่างกับเลขอ้างอิงจาก e-GP เป็นข้อมูลแยกตามความหมาย ไม่สร้างหรือจองเลข e-GP แทนระบบภายนอก

การเปลี่ยนฉบับหลักหลังออกเอกสารหรือส่งคลังต้องมีรุ่น/ประวัติและรายการที่ได้รับผลกระทบ ฉบับลงนามและ manifest เก่าไม่เปลี่ยนย้อนหลัง การมีสแกนลงนามของต้นฉบับ e-GP ไม่ทำให้ร่างที่สร้างใหม่ได้รับสถานะลงนามแล้วไปด้วย

ในโหมดไฟล์ให้แสดงต้นฉบับเป็นตัวอย่าง ในโหมดร่างให้แสดง A4 ที่ระบบสร้าง มีป้ายแหล่งที่มาและโหมดที่เลือกใน UI โดยไม่ใส่ข้อความ UI ทับลงบนต้นฉบับหรือพิมพ์ป้ายที่ไม่ได้กำหนดในแม่แบบ

รหัส E/P/V/F เป็นรหัสออกแบบเพิ่มเติม ไม่ใช่เลขทะเบียนราชการ รหัส D10 ในบทวิเคราะห์ไฟล์เก่าหมายถึงรูปพัสดุ แต่ข้อกำหนดล่าสุดเพิ่ม D10 ข้อมูลสาระสำคัญ e-GP จึงต้องเก็บความสัมพันธ์กับไฟล์เก่าและ P01 ให้ชัด ห้ามย้ายความหมายด้วยการเขียนทับไฟล์เดิม

ใช้ตัวร่างและเครื่องจัดหน้าเดิมกับเอกสารทำเอง D05–D11 ในโหมดร่าง และหน้ารวบรวมภาพ ส่วนโหมดไฟล์ e-GP/e-LAAS มีหน้าดูต้นฉบับ แนบ จัดลำดับ และพิมพ์ เก็บต้นฉบับโดยไม่แปลงเนื้อหาทับ และแยกฉบับร่างจากไฟล์ที่ระบบภายนอกออกให้

เอกสารต้นแบบที่มีชื่อร้าน ยอด วัน ปี หรือข้อความตกค้างไม่เป็นค่าจริงเริ่มต้น สร้างชุดข้อมูลจำลองที่สอดคล้องกันสำหรับตรวจรับ โดยรักษาต้นฉบับอ้างอิงไว้

แม่แบบต้องมีรหัส รุ่น ช่องข้อมูลที่อ่านได้ รายการช่องจำเป็น และประวัติการเปลี่ยน ข้อความตามระเบียบต้องมีที่มาและขอบเขต ไม่สร้างหรือแก้ข้อกฎหมายด้วย AI อัตโนมัติ

## 7 หน้าทำงานและกระบวนการหลัก

เพิ่มเมนูจัดซื้อจัดจ้างในกลุ่มงานประจำ เชื่อมเรื่องกับงานของฉันและโครงการเดิมได้ หน้ารวมแสดงงานที่ต้องทำต่อ เช่น รอข้อเสนอ รอส่งมอบ รอตรวจรับ รอเอกสาร ส่งคลัง ถูกตีกลับ และใกล้ครบกำหนด

หน้าเรื่องมีข้อมูลกลาง รายการ/ข้อเสนอ ผู้เกี่ยวข้อง สัญญาและกำหนดเวลา เอกสารแยกที่มา หลักฐาน/ตรวจรับ ชุดส่งตั้งหนี้รอบแรก ชุดฎีการอบสอง และประวัติ หน้ารวมมีรายการ “ควรทำต่อ” ที่อธิบายกำหนดและงานที่ต้องเสร็จก่อนได้

หน้าแก้เอกสารใช้การกรอกด้านซ้ายและ A4 ด้านขวาตามฟอร์มร่างหนังสือเดิม สลับเอกสารในเรื่องเดียวกันได้ แสดงที่มาของช่องที่ใช้ข้อมูลกลาง และเตือนก่อนออกเมื่อมีการแก้ที่ยังไม่บันทึก

กระบวนงาน:

สร้างเรื่องและเก็บเอกสารผู้ค้า → ตรวจข้อมูล/งบ/ผู้เกี่ยวข้อง → ร่างเอกสารทำเองและแนบไฟล์ e-GP/e-LAAS ตามขั้น → ติดตามสัญญา/ส่งมอบ/ตรวจรับ → รวมชุด A4 ให้ผู้เกี่ยวข้องลงนามและสแกนเก็บ → ส่งตั้งหนี้และเก็บหลักฐานคลังลงรับรอบแรก → รอคลังแจ้งและส่งเอกสารกลับให้ทำฎีกาต่อ → เจ้าของเรื่องทำฎีกาใน e-LAAS และรับไฟล์จริง → พิมพ์ A4 ให้ผู้มีอำนาจลงนามและสแกน → ส่งคลังอีกครั้ง → เก็บหลักฐานลงรับรอบสองและปิดงานของเจ้าของเรื่อง

สร้างรายการเอกสารที่ต้องมีล่วงหน้าได้ เอกสารทำเองและรายการที่เลือกโหมดร่างสร้างร่างล่วงหน้าได้ ส่วนโหมดไฟล์ภายนอกที่ยังไม่ได้รับให้แสดงรอแนบต้นฉบับ ความพร้อมของรายการตรวจตามโหมดที่เลือก ไม่ตีความการมีไฟล์อ้างอิงหรือการเลือกโหมดว่าพร้อมใช้ทันที ข้อมูลที่ยังไม่ทราบต้องแสดงว่ายังไม่ครบ ไม่มีการเติมเลข วันที่ ผลอนุมัติ ผลตรวจรับ ผลตั้งหนี้ หรือสถานะจ่ายให้เอง

## 8 กติกาจัดหน้า A4

- ใช้ฟอนต์ ระยะขอบ ระยะบรรทัด และพื้นที่ลงนามของแบบที่ตรวจรับ แยกจากสไตล์ UI
- วัดพื้นที่หลังฟอนต์และรูปพร้อมแล้ว ใช้ผลจัดหน้าที่วัดจริงสำหรับ preview และ PDF
- เก็บหัวข้อกับข้อความต้นเรื่องที่เกี่ยวข้อง และไม่แยกชื่อออกจากตำแหน่ง/ช่องเซ็นของคนเดียวกัน
- ผู้เสนออยู่ต่อจากข้อเสนอหรือข้อความสรุป ชุดความเห็นและช่องเซ็นพยายามอยู่บนหน้าเดียวกัน
- หากพื้นที่ไม่พอ ให้ย้ายชุดลงนามพร้อมข้อความเชื่อมที่จำเป็นไปหน้าถัดไป ค่าตั้งต้นนำข้อความท้ายอย่างน้อย 2 บรรทัดไปด้วยเมื่อทำได้ นี่เป็นกติกาออกแบบ ไม่ใช่การอ้างข้อบังคับตามกฎหมาย
- ไม่ลดขนาดตัวอักษรหรือระยะว่างให้ต่ำกว่าแบบที่ตรวจรับเพื่อบังคับให้จบหน้าเดียว
- รองรับจุดขึ้นหน้าใหม่ที่ผู้ใช้กำหนดและการคืนเป็นจัดหน้าอัตโนมัติ
- ตารางต่อหน้ามีหัวตารางซ้ำ แถวที่สูงเกินหนึ่งหน้าต้องแจ้งให้แก้หรือใช้รูปแบบที่รองรับ ไม่มีข้อความถูกซ่อน
- วัดพื้นที่ footer ตามข้อความจริง หากเรื่องหรือเลขยาว ต้องขยายพื้นที่และจัดเนื้อหาใหม่ ไม่ทับเนื้อหาหรือช่องเซ็น
- ถ้าชุดลงนามสูงเกินพื้นที่หนึ่งหน้า ให้แสดงเหตุและทางเลือก เช่น ปรับแบบหรือแยกหน้าความเห็น ห้ามตัดหรือย่อชื่อ/ตำแหน่งเงียบ ๆ

## 9 ข้อความใบต่อ

ใช้กับหน้า 2 เป็นต้นไปของเนื้อหาบันทึกฉบับเดียวกัน:

> ใบต่อบันทึกข้อความ เรื่อง {document.subject}
> ที่ {document.number} ลงวันที่ {document.dateThai}

เลขหน้าท้องถิ่นของหนังสือเพิ่มได้ตามแบบ เช่น หน้า 2/3 โดยไม่นับรวมหนังสือฉบับอื่นในแฟ้ม หน้าแรกไม่แสดงข้อความใบต่อ ส่วน TOR ภาพหรือเอกสารแนบที่เริ่มเป็นฉบับใหม่ใช้การระบุเอกสารแนบของตนเอง

แก้เรื่อง เลข หรือวันที่ในระบบแล้วใบต่อทุกหน้าต้องเปลี่ยนตาม ไม่มีข้อมูลซ้ำที่แก้แยกได้ และไม่คัดลอก footer เรื่องซ่อมจากไฟล์เก่ามาใช้

สำหรับ Word ให้ตรวจวิธีใช้ header/footer จริงร่วมกับข้อมูลอ้างอิงและฟิลด์เลขหน้า แยก first-page footer และเอกสารแนบอย่างถูกต้อง หากใช้ REF/DOCPROPERTY ต้องมีค่าแสดงล่าสุดตอนส่งออก พร้อมแจ้งวิธีอัปเดตฟิลด์เมื่อแก้ใน Word ก่อนพิมพ์ ไม่สมมติว่า Word จะอัปเดตฟิลด์ทุกชนิดทันทีเมื่อพิมพ์แก้ข้อความ

เมื่อนำกลับเข้าในระบบ สร้างใบต่อใหม่จากข้อมูลเฉพาะฉบับที่ผ่านตรวจแล้ว ไม่ยอมให้ข้อความ footer เก่ามาเขียนทับข้อมูลกลาง

## 10 ชุดช่องลงนาม

หนึ่งช่องเก็บรหัสคงที่ บทบาท ชื่อ ตำแหน่ง/ข้อความปฏิบัติราชการแทน หัวข้อความเห็น เนื้อหาหรือเส้นว่างสำหรับความเห็น พื้นที่ลงลายมือชื่อ และวันที่ตามแม่แบบ

รองรับ 3 แบบ:

1. เรียงเยื้องตามสายเสนอ โดยผู้เสนออยู่ใต้ข้อเสนอ และผู้ให้ความเห็น/ผู้มีอำนาจเรียงตามลำดับที่มองเห็นได้
2. สองคอลัมน์สำหรับประหยัดพื้นที่ โดยคงความสัมพันธ์และลำดับบทบาท
3. จัดวางเอง โดยลากช่องทั้งชุด มีแนวช่วยวาง ปรับพิกัดผ่านช่องกรอกได้ และคืนตำแหน่งแนะนำได้

เก็บตำแหน่งจริงเป็นหน่วยมิลลิเมตรสัมพันธ์กับพื้นที่พิมพ์ พร้อมจุดยึดกับส่วนเนื้อหา/ชุดลงนาม ไม่เก็บเฉพาะ pixel ของหน้าจอหรือเลขหน้าที่อาจเปลี่ยนเมื่อเนื้อหายาวขึ้น

ตรวจการทับกัน ขอบพิมพ์ เนื้อหา และ footer หลังการเปลี่ยนข้อความ ขนาด ตำแหน่ง หรือฟอนต์ ตำแหน่งที่ใช้ไม่ได้ต้องแสดงเหตุและไม่ถูกถือว่าพร้อมออกฉบับจริง

การขยับช่องไม่เปลี่ยนบทบาทหรือผลอนุมัติ รูปแบบมีได้ทั้งค่าเริ่มต้นของหน่วยงานและค่ารายฉบับ การบันทึกทับค่าเริ่มต้นต้องเป็นการเลือกของผู้ใช้โดยชัดเจน

ภาพลายเซ็นเป็นวัตถุแยกที่ผูกกับช่องได้ แยกจากชื่อ/ตำแหน่งและพื้นที่เซ็นเปล่า ไม่ถือว่าการเพิ่มภาพคือการอนุมัติออนไลน์หรือลงนามด้วยใบรับรอง

## 11 แก้ Word ภายนอกและนำกลับแบบตรวจความต่าง

ความสามารถนี้เป็นข้อกำหนดหลักของชุดแรก ไม่ถือว่านำเข้า Word แล้วสร้างร่างใหม่เพียงอย่างเดียวทดแทนได้

### 11.1 ตอนส่งออก

- ให้เอกสาร ขอบเขตข้อความ ย่อหน้า ตาราง รายการ และช่องลงนามมีรหัสคงที่ที่อ่านกลับได้
- ทดสอบการใช้ content controls/SDT tags หรือโครงสร้าง OOXML ที่คงรหัสผ่านการแก้ใน Microsoft Word ก่อนเลือกวิธีจริง ตรวจ API ของไลบรารีที่ติดตั้ง ไม่สมมติว่ารองรับ
- สร้าง exportId และบันทึก baseline เชิงโครงสร้างที่ใช้ส่งออกจริง รวมเนื้อหาหลังแก้เฉพาะฉบับ รุ่นข้อมูลกลาง รุ่นเอกสาร รุ่นแม่แบบ และ hash
- ใส่ข้อมูลช่วยระบุต้นทางใน .docx โดยไม่มีค่าลับหรือข้อมูลบัญชีเชื่อมต่อ เก็บ baseline ที่เชื่อถือได้ใน SQLite
- ข้อความและตารางที่ต้องแก้ต้องเป็นข้อความและตารางจริง ไม่ทำหนังสือทั้งหน้าเป็นภาพ

### 11.2 ตอนเลือกไฟล์นำกลับ

ผู้ใช้เลือกเรื่องและฉบับเป้าหมาย → แนบ .docx → ตรวจชนิด/ขนาด/โครงสร้าง → หา baseline ที่ตรง → แสดงความต่าง → เลือกผลรายจุด → ดู A4 ใหม่ → บันทึกเป็นรุ่นร่างใหม่

ไม่ใช้ชื่อไฟล์เป็นตัวพิสูจน์ว่าเป็นฉบับเดียวกัน ข้อมูล ID ในไฟล์เป็นเพียงตัวช่วย ต้องตรงกับเอกสารที่ผู้ใช้เลือกและ baseline ในฐานข้อมูล ไฟล์อัปโหลดไม่กำหนดสิทธิ์ สถานะอนุมัติ หรือเจ้าของข้อมูลให้เอง

### 11.3 เทียบสามรุ่น

| รุ่น | ความหมาย |
| --- | --- |
| เดิม | ข้อมูลที่ส่งออกพร้อม exportId นั้น |
| ในระบบ | เอกสารที่มีผลจากข้อมูลกลางและการแก้เฉพาะฉบับล่าสุด |
| ใน Word | ข้อมูลที่อ่านจากไฟล์นำกลับ |

แยกเป็น ไม่เปลี่ยน แก้เฉพาะในระบบ แก้เฉพาะใน Word แก้ตรงกัน และแก้ชนกัน แม้พบการแก้เพียงฝั่งเดียวก็ต้องให้ผู้ใช้เห็นรายการก่อนยืนยันนำกลับ ไม่มีการบันทึกทับขณะอัปโหลด

ตัวอย่าง: ส่งออกยอด 1,520 บาท ต่อมาในระบบเป็น 1,600 และ Word เป็น 1,700 ต้องแสดงทั้งสามค่าให้เลือก ไม่ตัดสินจากเวลาที่ใหม่กว่าหรือเลือก Word โดยอัตโนมัติ

หน้าตรวจความต่างให้เลือก:

- คงค่าในระบบ
- ใช้ค่าจาก Word สำหรับฉบับนี้
- แก้ค่ารวมเอง
- เสนอเปลี่ยนข้อมูลกลางของเรื่อง เมื่อเป็นช่องที่อนุญาต

### 11.4 การเปลี่ยนข้อมูลกลาง

การนำชื่อร้าน ยอดเงิน รายการ หรือบุคคลจาก Word กลับเป็นค่ารายฉบับไม่เปลี่ยนเรื่องทั้งชุดทันที ถ้าผู้ใช้เลือกเปลี่ยนข้อมูลกลาง ต้องแสดงเอกสารที่ได้รับผลกระทบและตรวจเงื่อนไขที่เกี่ยวข้อง

ยอดเงินที่อ่านได้ในย่อหน้าไม่เพียงพอที่จะเปลี่ยนราคาต่อรายการ ฐานภาษี หรือผลคัดเลือก หากเป็นยอดสรุปที่ไม่ทราบองค์ประกอบ ให้แสดงจุดที่ต้องแก้ในข้อมูลโครงสร้าง ไม่เดายอดย่อย

คำอ่านจำนวนเงินเป็นข้อมูลคำนวณ หาก Word เปลี่ยนให้ไม่ตรงตัวเลข ต้องแจ้งและให้แก้ต้นทาง ไม่รับตัวเลขกับคำอ่านที่ขัดกันโดยไม่แสดงสถานะ

### 11.5 กรณีโครงสร้างไม่ครบหรืออ่านกลับไม่ได้

- รองรับการอ่านกลับของข้อความ หัวข้อ ตารางพื้นฐาน ชื่อ ตำแหน่ง ความเห็น และข้อมูลเฉพาะฉบับที่ระบบสร้างเอง ได้แก่ D01–D04, D05–D11 เมื่อเลือกโหมดร่าง และ D12–D14 รวมหน้าประกอบที่ระบบสร้างและเปิดให้แก้ ส่วนไฟล์ต้นฉบับจาก e-GP/e-LAAS เป็นหลักฐานแยก ไม่ใช้การนำ Word กลับไปแก้ทับต้นฉบับ
- หากรหัสส่วนใดหาย ให้แสดงส่วนที่จับคู่ไม่ได้และให้เลือกจับคู่/สร้างส่วนใหม่เอง ไม่จับคู่อย่างมั่นใจเกินหลักฐาน
- หากไม่พบ baseline ห้ามอ้างว่าเป็นการเทียบสามรุ่น ให้ใช้โหมดเทียบไฟล์กับฉบับเป้าหมายพร้อมระบุข้อจำกัด หรือสร้างร่างแยก
- Track Changes ที่ค้างต้องแจ้งและให้ผู้ใช้เลือกมุมมองข้อความสำหรับเทียบ ไม่ยอมรับหรือปฏิเสธการแก้ทั้งหมดเงียบ ๆ ไม่แก้ไฟล์ต้นฉบับ
- ความเห็นของ Word รูป กล่องข้อความ วัตถุฝัง เซลล์ผสาน และการจัดวางที่ไม่รองรับต้องมีรายการชัดเจน เก็บต้นฉบับไว้และให้เปิดดูได้ ไม่ทิ้งเนื้อหาสำคัญโดยไม่แจ้ง
- การอ่าน Choice/Fallback ต้องเลือกข้อความอย่างเหมาะสม ไม่เพิ่มชื่อ/ช่องเซ็นซ้ำเพราะอ่านสอง representation ของวัตถุเดียวกัน
- อ่านการเปลี่ยนเนื้อหาแยกจากการเปลี่ยนรูปแบบ ไม่รับรองนำเค้าโครง Word ทุกชนิดกลับแบบ 1:1 ส่วนที่ต้องจัดใหม่ต้องแสดงให้เห็นและยังเป็นร่างรอตรวจ
- ระบบจัดหน้าใหม่หลังรวมข้อมูล ไม่ใช้เลขหน้า/พิกัดเดิมจาก Word โดยไม่ตรวจพื้นที่จริง

### 11.6 การบันทึกและประวัติ

ตรวจ version ของเรื่องและเอกสารอีกครั้งก่อนรวม ถ้ามีการแก้ระหว่างเปิดหน้าความต่าง ให้เทียบใหม่ บันทึกผลรวมเป็น transaction และใช้ request id ป้องกันยืนยันซ้ำแล้วสร้างรุ่นซ้ำ

เก็บไฟล์ Word ที่นำกลับ baseline รายการความต่าง ผลเลือก และความสัมพันธ์กับรุ่นที่เกิดใหม่ ในขอบเขตข้อมูลธุรกิจและการสำรอง

การนำกลับสร้างรุ่นร่าง ไม่เปลี่ยนฉบับออก/ลงนามแล้ว หากผู้ใช้ต้องแก้ฉบับนั้น ให้สร้างรุ่นใหม่ที่อ้างฉบับเดิมและบันทึกเหตุผล การสร้างฉบับทดแทนเป็นขั้นตอนแยกที่ตรวจได้

## 12 ข้อจำกัดของโค้ดเดิมที่ต้องเผื่อในการพัฒนา

- ตัวนำเข้า Word เดิมรองรับบันทึกข้อความ/หนังสือภายในและสร้างร่าง ไม่ได้มี export baseline หรือเทียบสามรุ่น ต้องเพิ่มกลไกนำกลับโดยไม่ทำให้ทางนำเข้าเดิมเสีย
- โครงสร้างเดิมแจ้งข้อจำกัดรูป กล่องข้อความ และความเห็นหลายผู้ลงนาม จึงต้องเพิ่มตัวอ่านข้อมูลเชิงโครงสร้างสำหรับแม่แบบที่ระบบสร้างเอง
- ตัวส่งออก Word เดิมใช้ข้อมูลหน้าที่วัดจาก HTML และสร้าง sections จากหน้าที่ได้ ต้องตรวจใหม่ว่า section/page break/paragraph flow เหมาะกับการแก้ Word ต่อและ footer อัตโนมัติหรือไม่ ห้ามสมมติว่านำไปใช้โดยไม่ปรับแล้วรองรับข้อกำหนดนี้ครบ
- Word และ PDF ใช้เครื่องจัดหน้าต่างกัน การแก้ Word อาจทำให้จำนวนหน้าเปลี่ยน ต้องทดสอบกับ Microsoft Word เป้าหมายและจัดหน้า/ตรวจ footer อีกครั้งหลังนำกลับ
- รายชื่อตารางใน backup/restore และชนิด owner ในแฟ้ม local/Drive ระบุไว้โดยตรง ตารางและไฟล์ใหม่ต้องเพิ่มให้ครบ

## 13 สถานะงาน หลักฐาน และการเงิน

แยกสถานะเรื่องออกจากสถานะเอกสาร เช่น ร่าง ตรวจทาน ออกฉบับ เก็บลงนาม แทนที่/ยกเลิก

สถานะเรื่องต้องแยกช่วงเตรียม/จัดซื้อ/สัญญา/ตรวจรับออกจากสองรอบคลัง ได้แก่ เตรียมชุดตั้งหนี้ ส่งตั้งหนี้แล้ว รอคลังลงรับรอบแรก รอคลังดำเนินการ คลังส่งกลับพร้อมทำฎีกา เตรียมฎีกา รอลงนามชุดฎีกา ส่งชุดฎีกาแล้ว รอคลังลงรับรอบสอง และเสร็จงานเจ้าของเรื่อง การตีกลับให้แก้มีชนิด/รอบกำกับ ไม่ใช้สถานะเดียวแทนการส่งกลับตามปกติ

checklist อ้างไฟล์หรือเหตุยกเว้นได้ การสร้าง PDF กดตรวจทาน หรือแนบภาพลายเซ็นไม่ทำให้ผลอนุมัติ ตรวจรับ หรือจ่ายเปลี่ยนเอง

บิลและการส่งคลังเก็บเลข วันที่ ยอด ประเภท หลักฐาน ผลตรวจ และเหตุที่ถูกตีกลับ บันทึกส่งซ้ำเป็นประวัติ ไม่เขียนทับเหตุการณ์เดิม วันส่งออกจากกองกับวันคลังลงรับเป็นคนละเหตุการณ์ การส่งรอบสองยังไม่ปิดงานจนมีหลักฐานคลังลงรับ

คลังตั้งหนี้รอบแรกเสร็จทราบจากเจ้าหน้าที่คลังแจ้งและส่งเอกสารกลับให้เจ้าของเรื่องดำเนินการต่อ ให้บันทึกวันที่ ผู้แจ้ง/ผู้รับกลับ และเอกสารที่กลับมา เลขตั้งหนี้เป็นข้อมูลเสริมเมื่อมี ไม่บังคับเลขที่ผู้ใช้ยังไม่ได้รับ และไม่เปลี่ยนเป็นเสร็จเพราะเวลาผ่านไป

การจ่ายเงินจริงแยกเป็นข้อมูลติดตามเพิ่มเติม ไม่ใช่ตัวปลดล็อกการปิดงานตามขอบเขตที่ผู้ใช้ยืนยัน และไม่ปิดภาระสัญญาหรือกำหนดติดตามอื่นที่ยังไม่เสร็จโดยอัตโนมัติ

เชื่อมรับเข้าวัสดุ/ครุภัณฑ์หลังผู้ใช้ยืนยันข้อมูลรับมอบจริง แยกจำนวนสั่ง ส่งจริง และรับจริง ป้องกันรับเข้าซ้ำจากการ retry

## 14 กฎตามระเบียบและแบบของหน่วยงาน

แยกความสอดคล้องของข้อมูลออกจากการตัดสินตามกฎหมาย เช่น ยอดรวมไม่ตรงหรืออ้างคนละร้านตรวจได้จากข้อมูล ส่วนวงเงิน วิธี อำนาจผู้ลงนาม การแต่งตั้ง ภาษี ค่าปรับ ลำดับวัน และ e-GP ต้องตรวจตัวบท/หนังสือเวียนปัจจุบันและขอบเขตงาน

แต่ละกฎมีแหล่งอ้างอิง ขอบเขต วันที่มีผล วันที่ทบทวน และระดับเตือน/บล็อก ไม่ย้ายตัวเลขหรือข้อสมมติจากคำขอเดิมมาเป็นกฎใช้จริงโดยไม่ตรวจ ไม่ถือว่ายอดต่ำเพียงอย่างเดียวเป็นเหตุเร่งด่วน

ตรวจแบบหนังสือและสายเสนอของหน่วยงานก่อนเปิดใช้แม่แบบจริง เรื่องที่ยังไม่ยืนยันให้แสดงรอตรวจเฉพาะจุด การพัฒนาข้อมูลกลางและเครื่องจัดหน้ายังดำเนินต่อได้

## 16 ลำดับลงมือและเกณฑ์จบแต่ละช่วง

### ช่วง A พิสูจน์แกนเอกสารก่อนขยายทุกแบบ

สร้างชุดข้อมูลจำลองและทดลอง D07 สองโหมดในเรื่องเดียว ได้แก่ ใช้ไฟล์จาก e-GP กับร่างในระบบจากข้อมูล e-GP เพื่อพิสูจน์การเลือกฉบับใช้งาน การรักษาต้นฉบับ ตารางราคา สายลงนาม footer และ Word ไป–กลับของฉบับร่าง ใช้ D01 ตรวจฟอร์มบันทึกที่ทำเอง และ D14 หรือกรณีตารางประกอบตรวจรูปแบบงบประมาณเพิ่มเติมตามความจำเป็น

ในช่วงนี้ต้องทดลองทั้งแนบ PDF จาก e-GP และแนบภาพ D10/E01 โดยรักษาต้นฉบับ แสดงที่มาสองชั้นของ E01 และจัดหน้าประกอบ A4 ได้

ทดลองแก้ Word จริงแล้วเทียบสามรุ่นกลับ ทั้งชื่อร้าน ยอด ข้อความ ชื่อ/ตำแหน่ง และตาราง พิสูจน์ทั้งการจัดหน้า 1–3 หน้าและ footer ถ้ากลไกยังทำไม่ได้ต้องแก้ในช่วงนี้ ไม่เลื่อนสองทางออกจากขอบเขตโดยไม่แจ้ง

### ช่วง B ข้อมูลเรื่องและแม่แบบครบชุด

เพิ่มเรื่อง รายการ ข้อเสนอ ร้านค้า บุคลากร สัญญา/กำหนด/งานก่อนหน้า และรายการเอกสารครบ D01–D14 พร้อม E/P/V/F ตามหัวข้อ 6 เอกสารทำเองและโหมดร่างมีการแก้เฉพาะฉบับ โหมดไฟล์ภายนอกมีต้นฉบับ/เลขอ้างอิง/สถานะรอแนบ D05–D11 เลือกโหมดแยกรายฉบับ แสดงผลกระทบเมื่อแก้กลางและความต่างกับต้นฉบับภายนอกโดยไม่เขียนทับไฟล์นั้น

### ช่วง C จัดหน้าและชุดลงนามครบ

ทำแบบเยื้อง สองคอลัมน์ และจัดเอง จุดยึดตามเนื้อหา collision/พื้นที่พิมพ์/footer การขึ้นหน้าใหม่ และการส่งออกที่ข้อความ/ตารางแก้ใน Word ต่อได้

### ช่วง D Word นำกลับครบขอบเขต

ครอบคลุมเอกสารทำเองที่ระบบสร้างตามหัวข้อ 6 และหน้าประกอบที่เปิดให้แก้ มีหน้าความต่างรายจุด การชนกัน การเปลี่ยนข้อมูลกลาง การจับคู่ที่ไม่ครบ ต้นฉบับนำกลับ และการบันทึกรุ่นโดยไม่ทับฉบับลงนามหรือหลักฐาน e-GP/e-LAAS

### ช่วง E หลักฐานและส่งเบิกครบกระบวนงาน

ทำเอกสารผู้ค้า สัญญาและลำดับงาน ส่งมอบ ตรวจรับ บิล ภาพ ลงนาม checklist ชุดส่งตั้งหนี้/ลงรับรอบแรก รอคลังส่งเอกสารกลับเพื่อทำฎีกา ชุดฎีกาจาก e-LAAS/ลงนาม/ลงรับรอบสอง การตีกลับให้แก้ที่แยกชนิด การส่งซ้ำ และการปิดงานเจ้าของเรื่อง โดยเชื่อมพัสดุ/งาน/โครงการตามการยืนยัน

### ช่วง F ตรวจรับและบรรจุใช้งาน

ทดสอบถดถอย สำรอง/กู้คืน แฟ้ม local/Drive ย้ายเครื่อง อัปเดตฐานเก่า และตรวจรูปแบบกับเจ้าหน้าที่/กองคลัง ใช้ข้อมูลจำลองแยกจากข้อมูลจริงจนกว่าจะเปิดใช้งานตามขั้นตอน

## 18 คำสั่งเริ่มงานสำหรับแชทพัฒนา

> อ่าน AGENTS.md, PRODUCT.md, design.md, docs/procurement-analysis-20261115.md และข้อกำหนดฉบับนี้ โดยใช้แหล่งเอกสารและกระบวนงานล่าสุดในหัวข้อ 6/6.1 และ 20–22 แทนข้อสมมติจากบทวิเคราะห์ไฟล์เก่า ตรวจโค้ดและข้อมูลจำลองก่อนแก้ เริ่มช่วง A ด้วย D07 สองโหมด: ใช้ไฟล์ e-GP และร่างในระบบจากข้อมูล e-GP เพื่อพิสูจน์การเลือกฉบับใช้งาน ตารางราคา การจัดหน้า/ช่องลงนาม/footer และ Word ไป–กลับของฉบับร่าง พร้อมแนบหลักฐาน e-GP/e-LAAS และตรวจ D01 ที่ทำเอง จากนั้นดำเนิน B–F ให้ครบ AC01–AC35 และวงจรเดโมหัวข้อ 19 รวมสัญญา งานก่อนหน้า เอกสารร้านค้า และการส่งคลังสองรอบซึ่งจบที่ลงรับรอบสอง รักษาข้อมูลจริงและงานเดิม ไม่ถือไฟล์ตัวอย่างเป็นข้อมูลจริงหรือกฎที่ยืนยันแล้ว ไม่ลด Word ไป–กลับเป็นการสร้างร่างใหม่เพียงอย่างเดียว ไม่สร้างเอกสารทับต้นฉบับจากระบบภายนอก และบันทึกผลทดสอบ/ข้อจำกัดตามจริง

## 19 วงจรพัฒนา ทดลอง และเปิดให้เห็นผล

ข้อกำหนดเพิ่มเติมจากผู้ใช้: ต้องการเห็นกระบวนการและทดลองผลลัพธ์ระหว่างพัฒนา ไม่รอรวมทุกอย่างแล้วจึงเปิดให้ดูครั้งเดียว

ดำเนินงานต่อเนื่องเป็นช่วงที่ตรวจสอบและย้อนกลับได้ ใช้ข้อมูลจำลองแยกจากฐานข้อมูลและบัญชีจริง คุณสมบัติที่มองเห็นได้ควรเปิดให้ทดลองทันทีที่ส่วนจำเป็นทำงานครบ ส่วนการแก้ตรรกะภายในแสดงกรณีทดสอบและผลลัพธ์ตัวอย่างที่สัมพันธ์กับงานจริง

แต่ละช่วงใช้วงจรเดียวกัน:

1. แจ้งว่ากำลังแก้ปัญหาใด ผลที่คาดว่าจะเห็น และส่วนที่ยังไม่พร้อม
2. พัฒนาในขอบเขตย่อยที่ทดลองจบกระบวนการได้ มีจุดย้อนกลับและรักษางานค้างของผู้ใช้
3. รันทดสอบที่จำเป็นกับพฤติกรรมที่เปลี่ยน หากไม่ผ่านให้แก้และตรวจซ้ำก่อนรายงานว่าผ่าน
4. เปิดหน้าทดลองด้วยข้อมูลจำลอง พร้อมขั้นตอนสั้น ๆ ให้ผู้ใช้ลอง หรือแสดงภาพ/คลิปประกอบเมื่อช่วยตรวจรายละเอียด
5. เมื่อเกี่ยวกับเอกสาร ให้ไฟล์ PDF/Word จริงที่สร้างจากรุ่นนั้น พร้อมตัวอย่างกรณีปกติและกรณีขอบเขต เช่น ข้อความ/ตำแหน่งยาว
6. สรุปสิ่งที่ทำงานแล้ว ผลตรวจที่ยืนยันได้ และประเด็นที่ต้องตัดสินใจ แล้วดำเนินงานย่อยถัดไปตามข้อกำหนดที่ตกลง

## 20 บริหารสัญญา กำหนดเวลา และลำดับงาน

รองรับทั้งสัญญาและใบสั่งซื้อ/จ้างที่เป็นข้อตกลงของเรื่อง เชื่อมกับ D09 คู่สัญญา เอกสารต้นทาง และข้อมูลสัญญาที่แสดงใน e-LAAS ตาม E01

### 20.1 กำหนดที่ต้องเก็บ

- เลข/ประเภทข้อตกลง วันลงนาม วันได้รับใบสั่ง วันเริ่มและสิ้นสุด ตามที่ปรากฏในหลักฐานจริง
- กำหนดส่งมอบรายงวด รายการ/จำนวนที่ต้องส่ง ผลส่งจริง ผลตรวจรับ และผู้รับผิดชอบติดตาม
- วิธีคำนวณกำหนด: จำนวนวัน จุดเริ่มนับ นับรวมวันแรกหรือเริ่มวันถัดไป วันปฏิทินหรือวันทำการ วันหยุดที่ใช้ และข้อความเงื่อนไขอ้างอิง
- วันเป้าหมายภายใน เช่น เตรียมชุดลงนาม ส่งตั้งหนี้ ติดตามคลัง เตรียมฎีกา และส่งคลังรอบสอง แยกจากวันครบกำหนดตามสัญญา
- งานที่ต้องเสร็จก่อน ระยะทำงาน/ระยะเผื่อที่ผู้ใช้กำหนด ผู้รับผิดชอบ ผู้ที่กำลังรอ และวันที่นัดติดตาม
- เหตุการณ์เปลี่ยนแผนและแก้ไขสัญญา พร้อมกำหนดเดิม/ใหม่ เหตุผล วันที่ และเอกสารอ้างอิง ไม่ถือว่าการเลื่อน task เป็นการขยายสัญญา

กำหนดส่งมอบตามสัญญาไม่เท่ากับกำหนดปิดขั้นตอนการเงินทุกอย่าง การตั้งหนี้/ฎีกาที่เกิดภายหลังมีวันเป้าหมายของตัวเอง ห้ามบังคับทุกกิจกรรมให้เกิดก่อนวันส่งมอบด้วยกฎเดียว

### 20.2 รายการควรทำก่อน

แสดงทั้ง “ควรทำต่อ” “ติดงานก่อนหน้า” และ “รอบุคคล/หน่วยงานอื่น” พร้อมเหตุผลและวันที่ ไม่ใช้สีหรือเปอร์เซ็นต์อย่างเดียว

1. งานเกินกำหนดต้องเห็นเด่น พร้อมแสดงงานก่อนหน้าที่กำลังขวางและสิ่งที่ทำได้จริงในวันนี้
2. งานที่พร้อมทำเรียงจากความเสี่ยงต่อกำหนดใกล้สุด โดยดูระยะทำงานที่เหลือและระยะเผื่อด้วย ไม่เรียงจากวันครบกำหนดอย่างเดียว
3. งานก่อนหน้าที่จะทำให้ส่งมอบ/ส่งคลังไม่ทันต้องถูกยกขึ้นมา เช่น ต้องได้ลายเซ็นก่อนส่งตั้งหนี้ จึงแนะนำตามลายเซ็นก่อนปุ่มส่งคลัง
4. งานที่รอคลังแสดงวันที่ส่ง/ลงรับ รออะไร ใครรับผิดชอบ และวันนัดติดตาม การรอไม่ทำให้งานสำเร็จเมื่อเวลาผ่านไป
5. ผู้ใช้ปรับความสำคัญและแผนภายในได้ โดยยังเห็นว่าขัดหรือเสี่ยงต่อกำหนดใด

เมื่อมีข้อมูลระยะทำงานครบ สามารถเสนอแผนย้อนจากวันเป้าหมายผ่านงานก่อนหน้า หากเริ่มช้าจนทำไม่ทัน ให้แสดงความเสี่ยงและงานที่ต้องเร่ง ไม่สร้างวันที่สำเร็จย้อนหลังหรือเปลี่ยนกำหนดสัญญาให้เอง หากระยะทำงานยังไม่ทราบ ให้เรียงตามข้อมูลที่มีและระบุข้อมูลที่ขาด

ตรวจวงวนของงานก่อนหน้าและกำหนดที่ขัดกัน รองรับหลายงวดและการรับมอบบางส่วน โดยไม่ปิดงวดอื่นจากการตรวจรับเพียงงวดเดียว

### 20.3 แจ้งเตือนและประวัติ

ใช้ระบบงาน/ปฏิทิน/แจ้งเตือนเดิมเท่าที่เหมาะสม แสดงวันคงเหลือ ก่อนครบกำหนด ถึงกำหนด และเกินกำหนดตามค่าของผู้ใช้ ไม่เพิ่มกำหนดตามกฎหมายที่ยังไม่ได้ตรวจ การเปิดกลับมาต้องเห็นงานค้างและกำหนดที่ผ่านมาได้ การเตือนขณะปิดโปรแกรมต้องไม่ถูกอ้างว่ารองรับจนมีส่วนทำงานเบื้องหลังและทดสอบจริง

การปิดงานเจ้าของเรื่องที่คลังลงรับรอบสองไม่ทำให้ภาระสัญญาหรือกำหนดติดตามอื่น เช่น งวดที่ยังไม่รับหรือรายการที่ผู้ใช้ยังเปิดติดตาม ถูกปิดโดยอัตโนมัติ แยกสถานะงานธุรการออกจากสถานะข้อตกลง

## 21 แฟ้มหลักฐานผู้ค้า เอกสารภายนอก และชุดกระดาษ

### 21.1 หมวดเอกสาร

รับไฟล์สแกน PDF และภาพตามชนิดที่ระบบรองรับ แนบหลายหน้า/หลายไฟล์ต่อเรื่องได้ แบ่งอย่างน้อยเป็น:

- ใบเสนอราคาและเอกสารประกอบข้อเสนอ
- ใบมอบอำนาจและเอกสารผู้มอบ/ผู้รับมอบตามที่ได้รับจริง
- เอกสาร VAT/ภาษี โดยระบุชนิดจริง เช่น ใบกำกับภาษี เอกสารจดทะเบียน หรือเอกสารอื่น ไม่สมมติว่าทั้งหมดเป็นเอกสารชนิดเดียว
- ใบส่งของ ใบแจ้งหนี้ ใบเสร็จ และหลักฐานอื่นของร้านค้า
- เอกสาร/ภาพจาก e-GP, E01 ที่แสดงใน e-LAAS, ชุดฎีกาจาก e-LAAS
- ภาพพัสดุ/หน้างาน/ส่งมอบ และฉบับสแกนหลังลงนาม
- ใบส่ง ตราลงรับ และเอกสารที่คลังส่งกลับ แยกตามรอบ

ทะเบียนร้านค้าช่วยค้นและใช้ข้อมูลซ้ำได้ แต่แฟ้มเรื่องต้องบันทึกว่าครั้งนี้ได้รับเอกสารใด ฉบับใด วันที่ใด เอกสารมอบอำนาจ/เอกสารที่มีระยะหรือขอบเขตใช้ต้องไม่ถูกถือว่าใช้ได้ตลอดทุกเรื่องโดยไม่มีการตรวจ

### 21.2 ต้นฉบับและที่มาสองชั้น

ไฟล์เก็บอย่างน้อย owner เรื่อง/สัญญา/เอกสาร/งวด/รอบคลัง หมวด ชื่อผู้ออก/ผู้ส่ง ช่องทางได้รับ วันที่เอกสาร วันที่รับ/แคป เลขที่ถ้ามี hash ชนิด/ขนาด รุ่น และสถานะเจ้าหน้าที่ตรวจ

แยกข้อมูลต้นทางออกจากหน้าจอที่ได้ภาพ เช่น:

| หลักฐาน | ต้นทางข้อมูล | ระบบที่แสดง/แคป |
| --- | --- | --- |
| D10 ข้อมูลสาระสำคัญ | e-GP | e-GP |
| E01 ข้อมูลสัญญา | e-GP | e-LAAS |
| F03 เอกสารวางฎีกา | e-LAAS | e-LAAS หรือไฟล์ที่ได้รับจากระบบนั้น |

E01 ต้องมีชื่อที่อ่านรู้เรื่อง เช่น “ข้อมูลสัญญา e-GP ที่แสดงใน e-LAAS” เก็บเลขโครงการ/สัญญาที่ใช้จับคู่เมื่อมี ผู้ใช้เป็นผู้เข้าใช้ระบบภายนอกและนำไฟล์/ภาพมาแนบ การเชื่อม e-GP กับ e-LAAS เป็นลักษณะข้อมูลที่ผู้ใช้อธิบาย ไม่ใช่การเชื่อม API ใหม่ที่ระบบสารบรรณทำแล้ว

เก็บต้นฉบับทุกฉบับแยกจากสำเนาจัดพิมพ์ ภาพที่หมุน ตัดขอบ หรือจัด A4 ต้องไม่เขียนทับภาพต้นทาง รุ่นใหม่อ้างรุ่นเดิมได้และยังเปิดดูหลักฐานที่เคยส่งคลังได้

### 21.3 พิมพ์ A4 ลงนาม สแกน และชุดส่ง

ระบบสร้างสารบัญและจัดลำดับชุดส่งตาม workflow ได้ มีจำนวนชุดพิมพ์ที่ปรับได้และตัวอย่างก่อนพิมพ์ ไฟล์จากระบบภายนอกที่จัดหน้าไว้แล้วคงเนื้อหาเดิม ส่วนภาพหน้าจอจัดลงหน้า A4 โดยรักษาสัดส่วนและความอ่านได้ หากภาพเล็ก/แตกหรือแบ่งไม่เหมาะ ต้องแสดงให้ตรวจ ไม่ยืดหรือสร้างข้อมูลในภาพขึ้นใหม่

เอกสารร่าง/ไฟล์ต้นทางกับฉบับลงนามเป็นคนละหลักฐาน หลังพิมพ์และเซ็นบนกระดาษให้นำสแกนกลับมาแนบฉบับที่ตรงกัน มีสถานะ “รอตรวจสแกน” และ “เจ้าหน้าที่ตรวจว่าลงนามครบแล้ว” ตามการบันทึกจริง ไม่มีการรับรองความแท้ลายเซ็นจากการพบรูปหรือกดครบ checklist

ก่อนส่งคลังแต่ละรอบ สร้าง packetId และ manifest ซึ่งตรึงรายการ/รุ่นไฟล์ ลำดับ จำนวนหน้า/ชุดเท่าที่ตรวจได้ เอกสารลงนามที่ใช้ และเจ้าของเรื่อง บันทึกตัวอย่างชุดที่พิมพ์หรือส่งเป็นหลักฐาน หากแก้เอกสารภายหลังต้องสร้างชุดส่งรุ่นใหม่ ไม่เปลี่ยน manifest ของชุดที่คลังรับแล้ว

บันทึกตำแหน่งแฟ้มกระดาษ/ผู้ถือเอกสารได้ เพื่อรู้ว่าต้นฉบับกำลังอยู่กับเจ้าของเรื่อง ผู้ลงนาม หรือคลัง ประวัติการส่งกลับช่วยตามต้นฉบับ ไม่ถือว่าไฟล์สแกนแทนกระดาษตัวจริงในทุกกรณี

ต้นฉบับ สแกน manifest และหลักฐานลงรับทั้งสองรอบต้องเข้า SQLite/สำรอง/กู้คืน/local dossier/Drive ตามนโยบายเดิม โดยเชื่อมไฟล์กับเจ้าของถูกต้องและไม่พึ่งพาธบน Desktop เป็นที่เก็บถาวร

## 22 กระบวนงานกองคลังสองรอบและจุดปิดงาน

กระบวนงานนี้อิงขั้นตอนจริงที่ผู้ใช้ยืนยันสำหรับหน่วยงานของตน ไม่ประกาศว่าเป็นลำดับตามกฎหมายสำหรับทุกหน่วยงาน

| ลำดับ | สถานะ/สิ่งที่ต้องทำ | หลักฐานหรือข้อมูลเปลี่ยนสถานะ |
| --- | --- | --- |
| 1 | เตรียมชุดเสนอเซ็น | ฉบับที่เลือกใช้งานตามโหมดของแต่ละรายการครบและตรวจแล้ว พร้อมต้นฉบับประกอบตามที่เลือก |
| 2 | พิมพ์ A4 และลงนาม | ตรวจรายเอกสาร เก็บสแกนฉบับลงนาม และรายการยังขาด |
| 3 | ส่งตั้งหนี้รอบแรก | ชุดส่งรอบแรก manifest และวันส่ง ผู้ส่ง/ผู้รับเท่าที่ทราบ |
| 4 | คลังลงรับรอบแรก | วันลงรับ เลขรับเมื่อมี และภาพตราลงรับ/ใบรับ/หลักฐานตามที่ได้รับ |
| 5 | รอคลังดำเนินการ | แสดงวันที่ส่ง/ลงรับ วันนัดติดตาม ผู้รับผิดชอบ และสิ่งที่รอ |
| 6 | คลังแจ้งและส่งเอกสารกลับให้ทำฎีกา | วันที่รับกลับ ผู้แจ้ง/ผู้รับ และเอกสารที่กลับมา ผู้ใช้บันทึกว่าเป็นการส่งต่อขั้นตอนปกติ |
| 7 | เจ้าของเรื่องทำฎีกาใน e-LAAS | บันทึกเลข/วันที่เมื่อได้จริง และแนบเอกสารวางฎีกาที่ระบบภายนอกออกให้ |
| 8 | พิมพ์ชุดฎีกา A4 และให้ผู้มีอำนาจลงนาม | ฉบับลงนามและการตรวจครบตามชุด |
| 9 | ส่งชุดฎีการอบสอง | packetId/manifest รอบสอง วันส่ง และเอกสารที่เกี่ยวข้อง |
| 10 | คลังลงรับรอบสอง | วันลงรับและหลักฐานที่ได้รับ เชื่อมกับชุดส่งรอบสอง |
| 11 | เสร็จงานเจ้าของเรื่อง | ปิดงานได้จากหลักฐานลงรับรอบสอง เก็บแฟ้ม/ประวัติครบ |

### 22.1 การส่งกลับที่ต้องแยก

- “ส่งกลับเพื่อทำฎีกาต่อ” คือคลังดำเนินการรอบแรกแล้วและแจ้งให้เจ้าของเรื่องรับเอกสารไปขั้นถัดไป ไม่ใช่ความผิดพลาด
- “ตีกลับให้แก้ไข/เพิ่มเอกสาร” บันทึกรอบคลัง รายการที่ขาด เหตุ วันที่ ผู้แจ้ง และผู้รับผิดชอบ แล้วกลับไปแก้เฉพาะส่วนที่เกี่ยวข้อง
- “รับเอกสารกลับ/ยืมเอกสาร” โดยยังไม่ได้ยืนยันว่าพร้อมทำฎีกา ไม่ปลดล็อกสถานะพร้อมทำฎีกาเอง

เมื่อส่งซ้ำ ให้เชื่อมการส่งครั้งใหม่กับรอบและครั้งก่อน คงหลักฐานเดิมไว้ เอกสารที่แก้หลังลงนามต้องกลับมาตรวจ/จัดการฉบับลงนามที่เกี่ยวข้องก่อนรวมเป็นชุดใหม่

### 22.2 เงื่อนไขบันทึก

วันส่ง วันลงรับ และวันรับเอกสารกลับเป็นคนละช่อง วันลงรับอาจต่างจากวันส่งได้ ไม่เติมให้เท่ากันอัตโนมัติ เลขรับ/เลขตั้งหนี้/เลขฎีกาเป็นข้อมูลตามที่มีจริงและยังบันทึกงานระหว่างรอเลขได้

การยืนยันว่าคลังทำรอบแรกเสร็จใช้การแจ้งและส่งเอกสารกลับจากเจ้าหน้าที่คลังตามกระบวนงานผู้ใช้ ไม่บังคับว่าต้องมีเลขตั้งหนี้อิเล็กทรอนิกส์เพื่อให้ระบบไปต่อได้ ผู้บันทึกต้องระบุเหตุการณ์และหลักฐานที่มีจริง ไม่อ้างว่าระบบดึงสถานะคลังอัตโนมัติ

ก่อนปิดงาน ต้องมีชุดส่งรอบสองและเหตุการณ์คลังลงรับที่อ้างชุดนั้น พร้อมหลักฐาน ไม่มีการปิดทันทีเพียงเพราะแนบไฟล์ฎีกาหรือกดส่ง และไม่ต้องรอให้มีสถานะจ่ายเงินจริงตามขอบเขตที่ผู้ใช้ยืนยัน

ตัวอย่างตรวจรับช่วง E ต้องสาธิตครบตั้งแต่ร้านค้าส่งเอกสาร งานตามสัญญาที่ใกล้ครบกำหนด เอกสารต้นทางหลายระบบ ชุด A4 ลงนาม ส่งตั้งหนี้ รอคลังส่งกลับ จัดฎีกา ลงนาม และคลังลงรับรอบสอง รวมการตีกลับให้แก้หนึ่งกรณีที่ไม่ปะปนกับการส่งกลับตามปกติ

การเขียนข้อกำหนดฉบับนี้ไม่ใช่การยืนยันว่าโมดูลหรือกฎตามระเบียบถูกพัฒนาและตรวจรับแล้ว
