# ผลพัฒนาช่วง A1 ห้องทดลองเอกสาร D07

วันที่ 15 พฤศจิกายน 2569

ความคืบหน้าเพิ่มเติม: แยกหน้าใหม่ `/procurement/template` ที่ใช้ต้นฉบับ Word จริงและตรวจฐานความเหมือนผ่านแล้ว ดู [ผลตรวจและขอบเขตแม่แบบต้นฉบับ](procurement-template-fidelity.md) รายละเอียดด้านล่างเป็นบันทึกห้องทดลองฟังก์ชันเดิม ไม่ใช่ข้อสรุปรวมของหน้าใหม่

อัปเดตจากการตรวจของผู้ใช้: รูปแบบเอกสารในห้องทดลองนี้ยังไม่ตรงต้นฉบับ ทั้งตำแหน่งลงนาม ตราครุฑ และรูปแบบข้อความ ผลทดสอบด้านล่างยืนยันเฉพาะฟังก์ชันที่ระบุ ไม่ใช่การผ่านเกณฑ์ความเหมือนต้นฉบับ ลำดับงานถัดไปเปลี่ยนเป็นทำแม่แบบจากสำเนา Word ต้นฉบับและเทียบหน้าต่อหน้าให้ผ่านก่อนขยายฟังก์ชัน ตามเกณฑ์ต้นเอกสารข้อกำหนดกลาง

เริ่มพัฒนาจาก [ข้อกำหนดกลาง](procurement-implementation-spec.md) โดยสร้างห้องทดลอง D07 ที่ใช้งานจริงบนเครื่อง เพื่อทดสอบข้อมูลกลาง การเลือกแหล่งเอกสาร การพิมพ์ A4 และการนำ Word กลับมาตรวจความต่าง ก่อนขยายไปทั้งกระบวนงาน ช่วงนี้เป็นส่วนแรกของ Stage A ยังไม่ถือว่า Stage A หรือระบบจัดซื้อจัดจ้างทั้งหมดเสร็จแล้ว

## เปิดทดลอง

เปิด <http://127.0.0.1:3107/procurement/lab> ขณะเซิร์ฟเวอร์ทดลองทำงาน หากต้องเปิดใหม่ ใช้ `npm run dev:procurement` จากโฟลเดอร์โครงการด้วย Node 22.13 ขึ้นไป แนะนำ Node 22 ที่เตรียมไว้ใน `.desktop/runtime/node.exe`

ข้อมูลเก็บแยกใน `output/procurement-lab/procurement-lab.sqlite` พร้อมไฟล์แนบ ฉบับส่งออก ฉบับฐาน และประวัติแก้ไข ต้องมีไฟล์ `SAFETY-TEST-ONLY` และเปิดตัวแปรห้องทดลองจึงเข้าถึงได้ ตัวเริ่มทดลองใช้พอร์ต 3107 และโฟลเดอร์ build แยกจากแอปหลัก โดยปิดการสำรองข้อมูลอัตโนมัติของแอปหลักในโหมดนี้ ไฟล์ Word ตัวอย่างบน Desktop ไม่ถูกนำมาแก้ไข

## สิ่งที่ทดลองได้แล้ว

- กรอกชื่อหน่วยงาน ผู้ขาย เลขหนังสือ วันที่ เนื้อหา รายการ ราคา ภาษี และผู้ลงนามสี่จุด แล้วบันทึกเป็นรุ่นใหม่ ข้อมูลยังอยู่หลังโหลดหน้าใหม่
- D07 เลือกใช้ไฟล์ต้นฉบับจากระบบ หรือร่างจากข้อมูล e-GP โดยยังเก็บทั้งสองส่วนไว้ และระบุไฟล์หลักได้
- แนบ PDF, PNG, JPEG และ DOCX ขนาดไม่เกิน 10 MB เก็บไฟล์ต้นฉบับพร้อม SHA-256; แสดง PDF/ภาพและข้อความช่วยตรวจจาก DOCX
- แสดงตัวอย่าง A4 และส่งออก PDF ที่จัดหน้าแล้ว ข้อความใบต่อหน้า 2 เป็นต้นไปใช้เรื่อง เลขหนังสือ และวันที่จากข้อมูลเอกสารเดียวกัน
- เลือกชุดลายเซ็นแบบเรียงเหลื่อมหรือสองคอลัมน์ ระบบย้ายชุดทั้งสี่ไปหน้าใหม่เมื่อพื้นที่ไม่พอ โดยเก็บข้อเสนอและหัวข้อไว้ด้วยกัน
- ส่งออก Word ที่แก้ข้อความและตารางได้จริง มีรหัสประจำช่อง ฉบับฐานที่จัดเก็บในฐานข้อมูล และท้ายหนังสือเป็น REF ที่อ้างอิง bookmarks บนหน้าแรก
- นำ Word กลับมาเทียบสามรุ่น เลือกคงค่าระบบ ใช้ค่าจาก Word หรือกรอกเองเป็นรายช่อง ก่อนบันทึกรุ่นใหม่ การเปิดหน้าตรวจไม่เปลี่ยนข้อมูล
- การแก้ข้อความนอกช่อง รูปภาพ และเนื้อหาที่ยังรวมไม่ได้ ต้องตรวจและยืนยันการเก็บไว้ในไฟล์นำกลับต้นฉบับ ช่องที่หายหรือมีรหัสซ้ำไม่ถูกเดาค่าหรือทับข้อมูลเงียบ ๆ
- ป้องกันบันทึกทับจากหน้าต่างที่ถือรุ่นเก่า และป้องกันนำผลเทียบที่ล้าสมัยมาใช้ การส่งผลรวมซ้ำไม่สร้างรุ่นซ้ำ

## ผลตรวจ

`tsc --noEmit` ผ่าน และทดสอบเฉพาะส่วนนี้ด้วย Vitest ผ่าน 6 กรณี ครอบคลุมจำนวนเงิน/ภาษี การเทียบสามรุ่น วันที่และตัวเลขไทย ช่อง Word ที่หาย/ซ้ำ การเก็บไฟล์และฉบับฐานหลังเปิดฐานข้อมูลใหม่ การตรวจรุ่นเก่า และการบันทึกผลรวมซ้ำ

ทดสอบด้วย Chrome ผ่านหน้าเว็บจริงครบตั้งแต่แนบไฟล์ เลือกฉบับหลัก บันทึก โหลดใหม่ สลับกลับเป็นร่าง ส่งออก Word แก้ทั้งในระบบและ Word เปิดความต่าง และเลือกค่ารวม ผลยืนยันว่าไฟล์อ้างอิงไม่เปลี่ยนแม้แต่ไบต์เดียว คำขอเปลี่ยนข้อมูลข้ามเว็บไซต์ถูกปฏิเสธ และไม่มีข้อผิดพลาด JavaScript ในเบราว์เซอร์ หน้าทดลองจำเอกสารที่เลือกผ่าน URL หลังโหลดใหม่ และตรวจหน้าจอขนาด 768/390 พิกเซลแล้วว่าไม่มีส่วนล้นแนวนอนนอกพื้นที่ตารางที่เลื่อนได้

PDF ตัวอย่างสั้นแบบสองคอลัมน์ 1 หน้า แบบเรียงเหลื่อมสั้น/ยาว 2 หน้า และยาวมาก 3 หน้า ตรวจภาพทุกหน้าและพื้นที่ท้ายหนังสือจริง ไม่อาศัยการอ่านข้อความจากไฟล์เพียงอย่างเดียว

Microsoft Word เปิด แก้และบันทึกสำเนาทดลองทั้งสี่แบบได้ โดยรักษาช่องข้อมูล 35 ช่องและ bookmarks 3 จุด การเปลี่ยนเลขหนังสือ/วันที่ในหน้าแรกอัปเดตท้ายหนังสือได้ และเมื่อนำกลับ ระบบพบเฉพาะช่องที่แก้จริง ทั้งยังแยกค่าผู้ขายที่เปลี่ยนฝั่งระบบไว้ก่อนหน้าได้ถูกต้อง

หลักฐานตรวจและไฟล์ทดลองอยู่ใน `output/procurement-stage-a/` ได้แก่ `validation.json`, `native-word-validation.json`, `native-word-roundtrip-validation.json`, `pdf-validation.json`, PDF/Word และภาพตรวจหน้าเอกสาร สคริปต์หลักอยู่ที่ `scripts/test-procurement-lab.mjs` และการตรวจด้วย Word อยู่ที่ `scripts/check-procurement-word.ps1`

## ข้อจำกัดและงานถัดไป

แม่แบบนี้เป็นต้นแบบทดสอบ ยังต้องเทียบถ้อยคำ รูปแบบ และเงื่อนไขกับผู้รับผิดชอบก่อนใช้จริง การตรวจความถูกต้องตามระเบียบไม่ได้สรุปจากตัวอย่างที่มีเพียงชุดเดียว

Word จัดหน้าด้วยกลไกของ Word จำนวนหน้าต่างจาก PDF ได้ ผลบนเครื่องนี้เป็น 2/3/4/2 หน้าสำหรับสั้น/ยาว/ยาวมาก/สองคอลัมน์ตามลำดับ หากต้องการพิมพ์ตามตัวอย่างบนเว็บให้ใช้ PDF ยังต้องปรับความใกล้เคียงของ Word ต่อใน Stage A โดยไม่ลดขนาดตัวอักษรอัตโนมัติ ตัวเรนเดอร์มาตรฐาน `render_docx.py` ใช้ไม่ได้เพราะเครื่องไม่มี LibreOffice จึงตรวจเพิ่มเติมด้วย Microsoft Word จริง ส่งออก PDF และเรนเดอร์ภาพผ่าน Poppler

ห้องทดลองนี้ยังไม่เชื่อมบัญชี e-GP/e-LAAS อัตโนมัติ ไม่มี OCR ไม่มีการลงลายเซ็นอิเล็กทรอนิกส์ และยังไม่รวมเข้าระบบสำรองข้อมูล/สิทธิ์หลายผู้ใช้ของแอปหลัก ต้องเตรียมส่วนเหล่านี้ก่อนใช้เก็บงานจริง

ลำดับถัดไปคือปรับแม่แบบ D07 และ Word ให้ตรงรูปแบบที่เลือก ตรวจ D01 และภาพ/ไฟล์ e-GP/e-LAAS ให้ครบ Stage A แล้วจึงพัฒนาข้อมูลกลางระดับเรื่องและแม่แบบที่เหลือ จากนั้นทำทะเบียนสัญญา กำหนดเวลาและลำดับงาน เอกสารผู้ค้า การส่งตั้งหนี้และคลังลงรับรอบแรก การคืนเอกสารให้เจ้าของเรื่องทำฎีกา และปิดงานเมื่อคลังลงรับรอบสอง ตามข้อกำหนดกลาง
